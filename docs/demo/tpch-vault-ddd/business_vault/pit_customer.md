# pit_customer

## Overview

| Property | Value |
|---|---|
| **Table Name** | `pit_customer` |
| **Type** | Point-in-Time |
| **Domain** | Business Vault |
| **Bounded Context** | Business Vault |
| **Grain** | One row per customer per snapshot date. |
| **Update Frequency** | daily |
| **Layer** | Business Vault |

A point-in-time index over the customer satellite. For every customer and every snapshot date it records which satellite row was current, so that a query for "what did we know about this customer in March" is an equi-join rather than a window function over the whole history.

## Columns

| Column | Type | Description |
|---|---|---|
| `customer_hk` | BINARY | Hash of the customer business key (FK) |
| `snapshot_date` | DATE | The date this row describes (PK, with customer_hk) |
| `sat_customer_details_ldts` | TIMESTAMP | Load date of the satellite row current on that date |
| `load_date` | TIMESTAMP | When this snapshot was built |

## Column-Level Lineage

| Column | Source Table | Source Column | Notes |
|---|---|---|---|
| `customer_hk` | `tpch.v_stg_customer` | `c_custkey` | Derived: `MD5` of the business key |
| `snapshot_date` | Generated by the snapshot job from its own calendar |  | Derived: one row per customer per day |
| `sat_customer_details_ldts` | `tpch.v_stg_customer` | `load_date` | Derived: the latest load date at or before the snapshot date |
| `load_date` | `tpch.v_stg_customer` | `load_date` |  |

## Relationships

Both parents are owned by Party. A point-in-time table has no keys of its own; it is entirely an index over somebody else's.

| Related Table | Join Key | Relationship |
|---|---|---|
| `hub_customer` | `c_custkey = customer_key` | Many-to-one |
| `sat_customer_details` | `load_date = sat_customer_details_ldts` | Many-to-one |

## Notes / Caveats

- The join to `hub_customer` is written on the business key names rather than the hash key names, and neither column exists on either table. It is left that way because it is the mistake a modeller makes when moving between the raw layer, which joins on hashes, and the source, which joins on business keys.
- The join to `sat_customer_details` is written satellite-column-first (`load_date = sat_customer_details_ldts`) on a `Many-to-one` row, which is the wrong way round. It is left that way on purpose: `load_date` exists on both tables and `sat_customer_details_ldts` on only one, so the orientation rule has to recover the true reading from the column lists rather than trusting the written order.
- `snapshot_date` records its source as prose because the snapshot calendar is generated by the job rather than read from anywhere.
