# bridge_customer_order

## Overview

| Property | Value |
|---|---|
| **Table Name** | `bridge_customer_order` |
| **Type** | Bridge |
| **Domain** | Business Vault |
| **Bounded Context** | Business Vault |
| **Grain** | One row per customer-and-order pair, per snapshot date. |
| **Update Frequency** | daily |
| **Layer** | Business Vault |

A precomputed walk of `lnk_order_customer`, carrying the presentation layer's surrogate key alongside both vault hash keys. It is the only table in the set that joins to both layers, which is what a business vault table is for: absorbing the awkwardness so neither layer has to know about the other.

## Columns

| Column | Type | Description |
|---|---|---|
| `customer_hk` | BINARY | The customer side, from the vault (FK) |
| `order_hk` | BINARY | The order side, from the vault (FK) |
| `customer_key` | STRING | The same customer, as the star knows them (FK) |
| `snapshot_date` | DATE | The date this walk was computed for (PK, with the hash keys) |
| `load_date` | TIMESTAMP | When this snapshot was built |

## Relationships

Three joins across three contexts and two modelling styles: two hubs in the raw vault and a dimension in the star.

| Related Table | Join Key | Relationship |
|---|---|---|
| `hub_customer` | `customer_hk = customer_hk` | Many-to-one |
| `hub_order` | `order_hk = order_hk` | Many-to-one |
| `dim_customer` | `customer_key = customer_key` | Many-to-one |

## Notes / Caveats

- `snapshot_date` records its source as prose because the snapshot calendar is generated by the job.
- Nothing depends on this table. It is rebuilt from scratch on every run and can be dropped without losing anything, which is why it is allowed to reach across boundaries the other contexts respect.
